# 1人実験の分析エンジン

> このプロジェクト（`self-experiment/`）の分析エンジン。事業全体の説明は [`../README.md`](../README.md)。

お客さんが**自分で選んで飲んでいるサプリ**が、**その人の記録の上で**差を生んでいるかを判定する。
勧めない。効くとも言わない。言うのは「あなたの記録で出た差」だけ。

```bash
pip install -r requirements.txt
python examples/make_example.py          # 見本の記録を作る（カフェイン15時、答え＝寝つき+8分）
python -m n1engine.run analyze examples/example.csv \
  --item "カフェイン（15時）" --outcome sol --substance caffeine --dose-hour 15 --out report.md
python -m n1engine.run substances        # 成分の一覧と、7日ずつの入れ替えに向いているか
python -m n1engine.run plan 普段の記録.csv --substance caffeine --dose-hour 15 --outcome sol
python -m pytest -q tests                # 壊れていないかの確認（50秒前後）
python scripts/calibrate.py              # 本格的な検証（10分前後）
```

## しくみの解説

### 1. 実験の設計（`design.py`）

28日を7日ずつ4つに分け、**普段通り → 飲む → 飲む → 普段通り**（またはその逆）にする。
期間は曜日がそろうよう7日の倍数に限る。

**月経周期を記録する人は56日（7日×8期間、ABABBABA）にする。** 28日の ABBA は「28日で1周する波」とほぼ同じ形をしていて、周期の長さが25〜35日のどれでも、どの日から始めても、周期の時期と飲んだ期間の重なりが0.89〜0.91になる（エンジンで計算、テストで固定）。周期で睡眠中の心拍は数拍/分動く（Shilaih 他 2017：黄体期中期は月経期より+3.8拍/分）ので、28日では周期の影響と飲んだ影響を分けられない。ABABBABA は重なり0.15以下。

真ん中で折り返すのは、季節や仕事の忙しさで体調が少しずつ変わる影響を、飲んだ期間と飲まない期間に均等に乗せるため。
前半は飲まず後半だけ飲むと、「飲んだから良くなった」のか「時間が経って良くなった」のか区別できない。

毎日の質問の順番もランダムに入れ替えて記録する。質問の順番で回答が偏ることは調査研究で確かめられていて、ランダムにすると偏りが平均される。記録した順番は、研究層（後述）の材料にもなる。

### 2. 判定の本体（`model.py`）

その日の記録を、次の足し算で説明する。

```
その日の記録 = 基準値
             + 差 × その日の曝露量   ← 知りたいのは「差」
             + 時間の流れによる変化
             + 外部要因（飲酒・休日・体調不良・月経周期の時期）
             + 揺れ（前日の揺れを一部引きずる）
```

**曝露量**は、成分の体内動態から計算した「その記録の時間帯に体に残っている量」（飲み続けて安定した状態=1.0）。次の「専門領域の層」で説明する。
気分・ストレス・睡眠・心拍などの**体の反応は補正に入れない**。飲んだことで動きうるものを補正に入れると、それを通じた差まで消える（v0.1.0 の検証で、本当の差1.0点が0.51点に縮んだ）。

**前日の引きずり**がこのエンジンの要。昨日疲れていた人は今日も少し疲れている。
この性質を無視して普通に比較すると、偶然の差を「差がある」と判定しすぎる。検証では、差がゼロなのに普通の比較は最大16.5%の確率で「差がある」と言った（CALIBRATION.md）。

**ベイズ**という考え方で、答えを確率で出す。「差がある／ない」の二択ではなく、「飲んだ期間の方が良かった確率は86%」「差の大きさは90%の見込みで−0.6〜+2.0点」という形になる。

計算は、上乗せ・揺れの大きさ・引きずりの強さを、他を仮に固定しながら何千回も推定し直し、そのばらつきを見る（ギブスサンプリング）。
記録が抜けた日があっても止まらない。抜けた日の前後のペアが使えなくなるだけ。

**事前の前提**は「たぶん差はない、あっても±2点程度」という控えめなものにしてある。実験前に固定し、レポートに書く。途中で変えない。
分・拍/分などの項目は、飲まない期間のばらつきを1点としてそろえてから同じ前提を使い、結果は元の単位に戻して出す。

**計算の確認**：出発点を変えた4本を並行に走らせ、同じ答えに落ち着いたかを R̂（1.01未満）と有効な推定回数（400回以上）で確かめ、レポートに載せる（Vehtari 他 2021 の基準）。

### 2.5 専門領域の層（`domain/`）

v0.1.0 は「飲んだ日=1、飲まない日=0」しか見ていなかった。v0.2.0 から、次の領域の知識を変数として持つ。

| 領域 | 何をモデルに入れたか | ファイル |
|---|---|---|
| 薬物動態学（成分が体内でどう吸収され、消えるか） | 1コンパートメントの経口モデル（Bateman式）で、記録の時間帯の体内量を毎日計算。飲み始めの立ち上がりと、やめた後の持ち越しが量として入る | `pk.py` |
| 成分ごとの数値 | 半減期・最高濃度までの時間・安定までの日数。**出典を確認できた値だけ**。カフェイン、L-テアニン、ビタミンD、オメガ3、マグネシウム | `substances.py` |
| 睡眠の記録（睡眠日誌） | Consensus Sleep Diary の項目：寝つくまで・途中で起きていた時間・眠っていた時間・睡眠効率・質 | `variables.py` |
| 自律神経・循環（装着型機器） | 睡眠中の心拍数、心拍変動 RMSSD（対数にして分析し、%で出す） | `variables.py` |
| 内分泌・時間生物学 | 月経周期の日を周期で1周する波（sin・cos）にして補正。設計の重なりを計算 | `variables.py`, `design.py` |
| 生活記録 | 飲酒・カフェイン飲料・休日・体調不良を外部要因として補正 | `variables.py` |

各項目は**役割**を持つ。

| 役割 | 例 | 分析での扱い |
|---|---|---|
| 体の反応 | 寝つき、睡眠の質、心拍、気分 | 主要項目（実験前に1つ決める）と参考項目。補正には使わない |
| 外部要因 | 飲酒、休日、体調不良 | 補正に使う（飲んだことで変わらない前提） |
| 周期 | 月経周期の日 | sin・cos にして補正に使う |
| 体内量を変えるもの | 実際に飲んだ時刻 | 曝露量の計算に使う |

**曝露量の計算（`pk.py`）**

```
1回飲んだ後の濃度  C(τ) = ka/(ka−ke) × (e^(−ke·τ) − e^(−ka·τ))     τ = 飲んでからの時間
ke = ln2 ÷ 半減期    ka = 最高濃度までの時間 Tmax から逆算
毎日の濃度 = それまでに飲んだ全部の重ね合わせ
曝露量 = 記録の時間帯（その夜23〜7時／日中9〜21時）の平均濃度 ÷ 飲み続けて安定したときの同じ時間帯の平均濃度
```

ここから3つのことが自動で出る。

1. **記録の時間帯に残る量。** カフェイン（半減期5時間）を8時に飲むと、その夜に残るのは1日の最高時の約9%、15時なら約24%、20時なら約48%
2. **7日ずつの入れ替えに向いているか。** 飲む期間と飲まない期間の体内量の差が、0/1で切り替わる場合の何%か。カフェイン99%（向いている）、半減期2日の成分67%（必要日数が約2.2倍）、ビタミンD 7%（向かない）。オメガ3は安定まで4〜6か月かかるので向かない。しきい値（85%・50%）はこのエンジンの決めごと
3. **実験前に空ける日数**（半減期の5倍）

前提：影響が体内量に比例する範囲で考える。半減期を半分や倍に誤ったときの影響は検証で測った（CALIBRATION.md）。

### 2.6 記録に現れるまでの遅れ（`domain/pd.py`、v0.3.0）

体の中の量が減っても、記録への影響はしばらく残ることがある（薬力学の持ち越し）。作用部位モデル（Sheiner 1979）と間接反応モデル（Dayneka 1993）は、影響が量に比例する範囲ではどちらも「体内量の一次の遅れ」になる。

```
記録に届く量(今日) = λ × 記録に届く量(昨日) + (1 − λ) × 体内量(今日)
λ = 0.5^(1 ÷ 遅れの半減期[日])      候補：0・0.5・1・2・3・5・7日
```

遅れの長さは、候補ごとの当てはまりを比べてギブスサンプリングの中で選び直す（事前の重みは「遅れなし」0.75）。レポートには遅れの見込みを表で出す。28日の記録では遅れの有無を見分ける力が弱いので、はっきりしないときはそう書く。遅れが無いと分かっている場合は `--no-pd` で切ると検出力が上がる。

### 2.7 外れた日に強い揺れ（v0.3.0）

揺れを裾の重い t 分布にする（Geweke 1993：正規分布の混合として表し、日ごとの重みも推定する）。体調を崩した日のように大きく外れた日の重みが自動で下がり、その日をレポートに出す。外れた日がない記録ではほぼ損をしない（CALIBRATION.md）。

### 3. シミュレーション（`simulate.py`）

答えの分かっている**偽の記録**を作れるので、3つの用途がある。

| 用途 | いつ | 何が分かるか |
|---|---|---|
| エンジンの検証 | 開発時 | 宣言した数字（「90%の幅」など）が実際に守られているか |
| 必要日数の見積もり | 実験前 | 最初の7日以上の記録から揺れ方を推定し、「あなたなら何日やれば差を見つけられるか」。記録が少ないうちは揺れ方の不確かさごと計算し、慎重な側に寄せる |
| 偶然との比較 | 実験後 | 「差がゼロでも、この程度の差は約21回に1回出る」。v0.2.0 から、時間の流れと外部要因を差し引いた後の差で比べる |

検証で、**本当に1点の差があっても、28日では半分以下の確率でしか「はっきり差がある」と言えない**ことが分かった。必要日数の見積もりは必須。

### 4. 中身を隠す上級版（`blinding.py`）

中身を知って飲むと、期待だけで体調が良くなる。分析をどれだけ工夫しても、中身を知った記録からは「成分の差」と「期待の差」を分けられない。

上級版では、空のカプセルと本物を家族などに入れ替えてもらい、本人は記録が終わるまで知らない。毎日「今日は本物を飲んだと思うか」も記録する。

- 本人の予想が半々より多く当たっていたら、隠しきれていなかった可能性を報告する（中身を隠した191人の研究でも、72%が自分の飲んだものを当てていた）
- 思い込みと記録の関係を、目安として並べて見せる。同じ研究では、実際の中身より「本物を飲んだと思ったか」の方が結果をよく予測した

思い込みは飲んだものの影響を受けて変わりうるので、思い込みで差を補正し直すことはしない。補正すると、飲んだ差の一部まで消してしまう。

### 5. レポート（`report.py`）

担当者がコメントを添えて納品する下書き。

- 「効果」「効く」「効力」を使わない（テストで自動確認している）
- 差がなかった場合も失敗として書かない。「この期間の記録からは違いが読み取れなかった。続けるかを気分ではなく記録で決められる材料になる」と書く
- 言えないことを必ず書く（期待との区別、他の人や成分そのものについては何も言えないこと、医療機関への相談）

見本：`examples/example_report.md`

## 研究層（`research/`）

**ここにあるものは顧客のレポートに使わない。**

### 質問の順番の量子モデル（`research/quantum.py`、`research/qq.py`）

心の状態をベクトル、質問への答えを軸への射影（Lüders の規則）で表す量子確率モデル（Wang & Busemeyer 2013）を、毎日の「はい／いいえ」2問（順番をランダムに入れ替える）に当てはめる。

| モデル | 中身 | パラメータ |
|---|---|---|
| 古典 | 順番に関係なく同じ同時確率 | 3 |
| 量子2次元 | 状態の角度 θ と、2つの質問の軸のなす角 φ。p(A=a の後 B=b) = \|⟨a\|ψ⟩\|² \|⟨b\|a⟩\|² | 2 |
| QQ | 「答えが食い違う割合は順番によらない」だけを課す | 5 |
| 自由 | 順番ごとに何も仮定しない | 6 |

`python -m n1engine.run quantum 記録1.csv 記録2.csv …` で、4つを BIC で比べ、QQ等式を尤度比で検定する。偽データでは、各順番300件なら作ったモデルを100%当てたが、1人分（各順番14件）では古典のデータの3割を量子と取り違えた。各順番50件を超えてから判断する。

### 複数人をまとめる階層モデル（`research/population.py`）

同じ成分・同じ主要項目の1人実験を、階層ベイズ（Zucker 他 1997）でまとめる。`python -m n1engine.run pool 記録1.csv 記録2.csv … --outcome sol --substance caffeine`。全体の平均・人による違い・次の1人の見込みを出す。成分の働きの話になるので、顧客のレポートや宣伝には使わない（社内で日数の見積もりに使う）。

### QQ等式の検証（`research/qq.py`）

質問の順番で回答が変わる現象について、量子確率モデルは「2つの質問の答えが食い違う確率は、どちらを先に聞いても同じ」という等式（QQ等式）を、事前に数値まで予測した。全米規模の調査70件と実験2件で支持されている（Wang 他 2014）。
一方、同じモデルの別の予測は多くのデータで成り立たず（Boyer-Kassem 他 2016）、同じ質問を繰り返すと同じ答えが返る現象との両立も未解決。体調の自己評価で検証した例は見つかっていない。

毎日「はい／いいえ」の質問の組を順番を入れ替えて聞いているので、同意を得た複数人の記録が溜まれば検証できる。1人の28日では足りない。成り立っても成り立たなくても、それ自体が新しい知見になるので、どちらの結果も公開する。

### 研究層から本番への昇格基準

すべて満たすまで、顧客のレポートには使わない。

1. 査読付きの論文で発表されている
2. 当てはめではなく、事前に数値を予測し、それが外部で確かめられている
3. 自社データで、分析方法を事前に決めて固定した上で、従来の方法より予測が当たることを、学習に使っていないデータで示した
4. 結果の言い方が「効力」の表現にならない

### 量子の出し方（ブランディング）

| 言える | 言えない（3を満たすまで） |
|---|---|
| 「量子認知の研究を、自社の記録データで検証しています」 | 「量子分析で精度が上がる」 |
| 「質問の順番による回答の偏りを、量子確率モデルで研究しています」 | 「量子で差が分かる」 |
| 研究の途中経過（成り立った／成り立たなかった）の公開 | 量子で出した結果を顧客のレポートに入れる |

1. 決まった間隔で関連論文を確認する（1人実験の統計、思い込みの扱い、量子認知）
2. 取り入れるものは研究層で自社データに当てて確かめる
3. 本番に移すときは版番号を上げ、CHANGELOG.md に「何を・なぜ・根拠」を書き、`scripts/calibrate.py` を再実行して CALIBRATION.md を更新する
