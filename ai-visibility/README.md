# ai-visibility — AI検索での見え方を測る

`docs/venture/01-start.md` の計測を自動化したもの。
**同リポジトリのカウンセリングアプリとは無関係の別事業のツール。** 切り出すときはこのディレクトリごと移す。

やることは1つだけ。

> 同じ質問を、複数のAIに、複数回投げて、誰の名前が出たかを記録し、レポートにする。

---

## なぜ「複数回」なのか

AIの回答は毎回揺れる。1回だけ投げると、**「たまたま出なかった」と「実際に出てこない」が区別できない。**

同じ質問を3回投げて、

- 3回とも出る → 安定して出ている
- 1回だけ出る → 揺らぎ。安定していない
- 0回 → 出ていない

と分ける。レポートでも「安定して出る」と「たまに出る」を合算しない。
合算すると実態を過大に見せることになり、翌週の再計測で必ず矛盾する。

---

## 使い方

```bash
npm install
cp .env.example .env            # ANTHROPIC_API_KEY を入れる
cp config/targets.example.json config/targets.json   # 計測対象を書く

node src/cli.js measure --dry-run   # 呼び出さずに質問一覧と回数を確認
node src/cli.js all                 # 計測 → 分類 → 集計 → レポート
```

週ごとに分けて実行する（差分が資産になるので、週を混ぜない）。

```bash
node src/cli.js all --week 2026-09-15
node src/cli.js all --week 2026-09-22
```

## 4つの段階

| コマンド | やること | 出力 |
|---|---|---|
| `measure` | 質問を各AIに投げ、**回答を全文そのまま**保存 | `data/<week>/raw.jsonl` |
| `classify` | 回答を構造化ラベルに落とす（論調・安全性への言及・登場した固有名） | `data/<week>/labels.jsonl` |
| `analyze` | ブランド別の出現率、質問別の安定性を集計 | `data/<week>/summary.json` |
| `report` | 顧客に渡す4部構成のレポートを生成 | `data/<week>/reports/<brand>.md` |

`measure` は**再開できる**。900回の途中で落ちても、再実行すると済んだぶんを飛ばして続きから走る。
失敗した呼び出しは記録に残るが「済み」には数えないので、再実行で拾い直される。

## 計測対象の書き方

`config/targets.json`（`targets.example.json` を参照）

```jsonc
{
  "category": "睡眠サポート系サプリ",
  "ingredients": ["グリシン", "GABA"],
  "concerns": ["寝つきが悪い"],
  "brands": [
    { "id": "brand-a", "name": "ブランドA", "aliases": ["BrandA"], "client": true },
    { "id": "brand-b", "name": "ブランドB", "client": false }
  ]
}
```

**`client: false` の競合も必ず入れる。** ここがこのツールの要点。

依頼主1社だけ測っても、納品して終わりの受託になる。競合20社を一緒に測れば、
1件の案件ごとにカテゴリ1つぶんのデータが手元に残る。追加コストはAPI代の数百円。
10社受注した頃には、業界横断の時系列データを持つことになる。
これが受託を資産に変える唯一の仕掛け（`docs/venture/02-growth.md`）。

`aliases` には表記ゆれを入れる。照合は全角/半角・カタカナ/ひらがな・記号を正規化してから行う（`src/normalize.js`）。

## 質問設計

`config/questions.js` の5型。重みつき。

| 型 | 重み | 理由 |
|---|---:|---|
| カテゴリ推薦（「〜におすすめのサプリは」） | 3 | 名前を知らない人の質問。売上に最も効く |
| 比較・選び方 | 3 | 購入直前の質問 |
| 成分の評価 | 3 | 否定されると売上が落ちる |
| 安全性 | 2 | 健康食品固有。購入をやめる理由になる |
| 指名（ブランド名で聞く） | 1 | **既に知っている人の質問なので事業インパクトが小さい** |

出現率はこの重みの加重平均。指名質問を重くすると「見えている」ように錯覚する。

## プロバイダ

| プロバイダ | 実装 | 有効化 |
|---|---|---|
| Anthropic | 公式SDK（`@anthropic-ai/sdk`） | `ANTHROPIC_API_KEY` |
| OpenAI | 公式REST | `OPENAI_API_KEY` + `OPENAI_MODEL` |
| Gemini | 公式REST | `GEMINI_API_KEY` + `GEMINI_MODEL` |

キーとモデルが揃っているものだけが計測対象に加わる。`--dry-run` で確認できる。

**すべて公式APIのみ。** 画面の自動操作や規約外の自動アクセスはしない。
事業の根幹が規約違反の上に載ると、いつ止まってもおかしくないうえ、
コンプライアンスが重い業界の顧客に説明できない。

有効化する前に、各社の利用規約で**「回答の記録・比較・第三者への提供」が許容されているか**を確認すること。

## 費用

呼び出し回数 = 質問数 × プロバイダ数 × 試行回数。

成分10・悩み5・ブランド20 の構成で質問は約35問、3プロバイダ×3回で **約315回**。
実費は各社の課金レートと実際の出力長で決まるため、**`--dry-run` で回数を確認し、
1回走らせて `raw.jsonl` の `usage` を集計して実測する**こと。ここで推定値を置くと必ず外れる。

分類（`classify`）は計測と同数の呼び出しが追加で走る。

## 設計上、譲っていない点

- **回答は全文そのまま保存する。** 捨てた情報は二度と取れない。「◯月時点ではこうだった」が言えることがこの事業の価値そのもの
- **揺らぎと変化を区別する。** 1回の違いで顧客にアラートを出すと、信用が一度で消える
- **レポートに提言を書かない。** 測定結果だけ。「こうすべき」を混ぜた瞬間にコンサルの営業資料になり、読まれなくなる
- **効果・効能や適法性の判断をしない。** 判断を売らないことが、法的な安全と中立の信用を同時に作る

## 他の事業への転用

このパイプラインは「同じ入力を複数回投げて、出力の差分と傾向をレポートにする」以上のことをしていない。
対象を差し替えるだけで別の事業になる（`docs/venture/04-other-models.md`）。
