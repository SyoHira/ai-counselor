# 1人実験の分析エンジン

> 同リポジトリのカウンセリングアプリとは無関係の別事業のツール。切り出すときはこのディレクトリごと移す。

お客さんが**自分で選んで飲んでいるサプリ**が、**その人の記録の上で**差を生んでいるかを判定する。
勧めない。効くとも言わない。言うのは「あなたの記録で出た差」だけ。

```bash
pip install -r requirements.txt
python examples/make_example.py          # 見本の記録を作る（答え＝1.2点の差）
python -m n1engine.run analyze examples/example.csv \
  --item "マグネシウム（就寝前）" --outcome-label "寝つきの良さ" --out report.md
python -m n1engine.run plan 普段の記録.csv  # 実験前に、何日必要かを見積もる
python -m pytest -q tests                # 壊れていないかの確認（30秒前後）
python scripts/calibrate.py              # 本格的な検証（4分前後）
```

## しくみの解説

### 1. 実験の設計（`design.py`）

28日を7日ずつ4つに分け、**普段通り → 飲む → 飲む → 普段通り**（またはその逆）にする。

真ん中で折り返すのは、季節や仕事の忙しさで体調が少しずつ変わる影響を、飲んだ期間と飲まない期間に均等に乗せるため。
前半は飲まず後半だけ飲むと、「飲んだから良くなった」のか「時間が経って良くなった」のか区別できない。

毎日の質問の順番もランダムに入れ替えて記録する。質問の順番で回答が偏ることは調査研究で確かめられていて、ランダムにすると偏りが平均される。記録した順番は、研究層（後述）の材料にもなる。

### 2. 判定の本体（`model.py`）

その日の記録を、次の足し算で説明する。

```
その日の記録 = 基準値
             + 飲んだ日の上乗せ      ← 知りたいのはこれ
             + 時間の流れによる変化
             + その日の気分・ストレス・睡眠の影響
             + 揺れ（前日の揺れを一部引きずる）
```

**前日の引きずり**がこのエンジンの要。昨日疲れていた人は今日も少し疲れている。
この性質を無視して普通に比較すると、偶然の差を「差がある」と判定しすぎる。検証では、差がゼロなのに普通の比較は最大16.5%の確率で「差がある」と言った（CALIBRATION.md）。

**ベイズ**という考え方で、答えを確率で出す。「差がある／ない」の二択ではなく、「飲んだ期間の方が良かった確率は86%」「差の大きさは90%の見込みで−0.6〜+2.0点」という形になる。

計算は、上乗せ・揺れの大きさ・引きずりの強さを、他を仮に固定しながら何千回も推定し直し、そのばらつきを見る（ギブスサンプリング）。
記録が抜けた日があっても止まらない。抜けた日の前後のペアが使えなくなるだけ。

**事前の前提**は「たぶん差はない、あっても±2点程度」という控えめなものにしてある。実験前に固定し、レポートに書く。途中で変えない。

### 3. シミュレーション（`simulate.py`）

答えの分かっている**偽の記録**を作れるので、3つの用途がある。

| 用途 | いつ | 何が分かるか |
|---|---|---|
| エンジンの検証 | 開発時 | 宣言した数字（「90%の幅」など）が実際に守られているか |
| 必要日数の見積もり | 実験前 | 最初の7日以上の記録から揺れ方を推定し、「あなたなら何日やれば差を見つけられるか」。記録が少ないうちは揺れ方の不確かさごと計算し、慎重な側に寄せる |
| 偶然との比較 | 実験後 | 「差がゼロでも、この程度の差は約21回に1回出る」 |

検証で、**本当に1点の差があっても、28日では半分以下の確率でしか「はっきり差がある」と言えない**ことが分かった。必要日数の見積もりは必須。

### 4. 中身を隠す上級版（`blinding.py`）

中身を知って飲むと、期待だけで体調が良くなる。分析をどれだけ工夫しても、中身を知った記録からは「成分の差」と「期待の差」を分けられない。

上級版では、空のカプセルと本物を家族などに入れ替えてもらい、本人は記録が終わるまで知らない。毎日「今日は本物を飲んだと思うか」も記録する。

- 本人の予想が半々より多く当たっていたら、隠しきれていなかった可能性を報告する（中身を隠した191人の研究でも、72%が自分の飲んだものを当てていた）
- 思い込みと記録の関係を、目安として並べて見せる。同じ研究では、実際の中身より「本物を飲んだと思ったか」の方が結果をよく予測した

思い込みは飲んだものの影響を受けて変わりうるので、思い込みで差を補正し直すことはしない。補正すると、飲んだ差の一部まで消してしまう。

### 5. レポート（`report.py`）

担当者がコメントを添えて納品する下書き。

- 「効果」「効く」「効力」を使わない（テストで自動確認している）
- 差がなかった場合も失敗として書かない。「この期間の記録からは違いが読み取れなかった。続けるかを気分ではなく記録で決められる材料になる」と書く
- 言えないことを必ず書く（期待との区別、他の人や成分そのものについては何も言えないこと、医療機関への相談）

見本：`examples/example_report.md`

## 研究層（`research/`）

**ここにあるものは顧客のレポートに使わない。**

### 量子認知の検証（`research/qq.py`）

質問の順番で回答が変わる現象について、量子確率モデルは「2つの質問の答えが食い違う確率は、どちらを先に聞いても同じ」という等式（QQ等式）を、事前に数値まで予測した。全米規模の調査70件と実験2件で支持されている（Wang 他 2014）。
一方、同じモデルの別の予測は多くのデータで成り立たず（Boyer-Kassem 他 2016）、同じ質問を繰り返すと同じ答えが返る現象との両立も未解決。体調の自己評価で検証した例は見つかっていない。

毎日「はい／いいえ」の質問の組を順番を入れ替えて聞いているので、同意を得た複数人の記録が溜まれば検証できる。1人の28日では足りない。成り立っても成り立たなくても、それ自体が新しい知見になるので、どちらの結果も公開する。

### 研究層から本番への昇格基準

すべて満たすまで、顧客のレポートには使わない。

1. 査読付きの論文で発表されている
2. 当てはめではなく、事前に数値を予測し、それが外部で確かめられている
3. 自社データで、分析方法を事前に決めて固定した上で、従来の方法より予測が当たることを、学習に使っていないデータで示した
4. 結果の言い方が「効力」の表現にならない

### 量子の出し方（ブランディング）

| 言える | 言えない（3を満たすまで） |
|---|---|
| 「量子認知の研究を、自社の記録データで検証しています」 | 「量子分析で精度が上がる」 |
| 「質問の順番による回答の偏りを、量子確率モデルで研究しています」 | 「量子で差が分かる」 |
| 研究の途中経過（成り立った／成り立たなかった）の公開 | 量子で出した結果を顧客のレポートに入れる |
